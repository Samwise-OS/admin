# Samwise-OS organization automation contract

**Contract version:** 1  
**Recorded:** 2026-10-30  
**Scope:** GitHub organization infrastructure on GitHub Free

This contract defines how the Samwise-OS organization baseline is declared, proposed,
reconciled, and accepted. The repository is the authority for desired values. Live
GitHub reads and observed user behavior remain the authority for whether those values
are effective.

## Sources of authority

`config/organization.json` declares organization identity and policy, the solo-owner
`Maintainers` team, provisioning defaults, Safe-Settings App metadata, and whether
scheduled repository reconciliation is enabled. `config/repositories.json` declares
managed repositories and immutable IDs. A new repository with no recorded ID is in
adoption-pending state; name equality never proves identity.

`.github/settings.yml` declares shared repository defaults. Per-repository rulesets
are generated by `scripts/generate_repository_settings.py` into
`.github/repos/<repository>.yml`, while `.github/deployment-settings.yml` is the
generated program allowlist. Do not edit generated files by hand. The generator's
`--check` mode, `scripts/validate_safe_settings.py`, and `scripts/audit.py validate`
must pass before any credentialed reconciliation step.

The Safe-Settings App is the repository-settings writer. Its installed selection and
permissions are separate from the versioned manifest and its generated allowlist.
The App currently selects `admin`, `.github`, `repository-template`, and
`baseline-canary`, with Repository Administration write, Contents read, Checks write,
and Metadata read. It does not own organization policy, team membership, repository
creation, or App installation changes. The authenticated owner CLI controller in
`scripts/organization.py` remains the writer for the explicitly declared organization
and team fields; there is no competing organization-policy writer.

## Repository lifecycle

An owner-authenticated local run of `scripts/provision.py` checks the immutable
administration workflow SHA, organization identity and active owner role. It compares
requested repositories with the authenticated org inventory and refuses ID mismatch.
Creation uses GitHub's create-from-template API for template-backed repositories and
the organization repository API for other declared repositories. A creation result
without a manifest ID requires adoption by recording the returned ID before another
reconciliation.

Shared-file updates use a deterministic branch based on the observed `main` SHA and
desired content, followed by an ordinary pull request. The provisioner checks the
remote base again before opening or reusing the pull request. It will not force-push an
unexpected branch or report pending review as convergence. Repository creation and
content review are distinct operations: review and merge the PR, observe successful
repository standards CI, and then run the provisioner again to establish convergence.

Adding a repository to `config/repositories.json` generates its Safe-Settings config
and expands the generated allowlist. It does not expand App authorization. The owner
must select the new repository in the installed App and verify that selection in
GitHub before a reconciliation can claim coverage. Repositories absent from the
manifest are unmanaged inventory; routine automation does not delete or archive them.
Visibility changes, deletion, archive, rename and transfer require separate owner
decisions and are outside normal convergence.

## CI and repository enforcement

PR and `main` governance validation is secretless with `contents: read`. The
`scripts/doctor.py` receipt records required commands, identity and outcomes, and its
artifact is published even after a failed check. No skipped, malformed or zero-test
result is accepted as a pass. The reusable
`.github/workflows/repository-baseline.yml` produces the stable check
`baseline / standards`; the `admin` workflow's required context is `governance`.

The generated ruleset payload requires active default-branch protection, no bypass
actors, deletion and non-fast-forward restrictions, linear history, pull requests,
resolved review threads, squash-only merge and the exact expected GitHub Actions app
integration for the required context. Repository-specific rules are compared to the
full named ruleset returned by GitHub, not only the list summary. A green local test,
configured payload, or visible check does not establish merge blocking. Functional
acceptance must use authenticated GitHub operations to prove that a failing normal PR
cannot merge, that a normal passing PR can merge, and that a direct update cannot
bypass the intended rule. See `docs/acceptance.md` for recorded outcomes and open
cases.

## Reconciliation and evidence

`.github/workflows/reconcile.yml` is the only Safe-Settings workflow. Dispatch from
`main` in preview mode first; review its plan before a manual apply. Before either
mode, it validates the generated configuration. It checks remote `main` against the
trusted checkout before preparation, again immediately before Safe-Settings reads the
remote config, and after the writer exits. Manual and scheduled runs serialize without
cancelling each other.

After the writer, `scripts/audit.py audit-managed` independently reads the declared
organization ID, each repository's immutable ID, canonical name and owner ID, shared
repository defaults, and each managed ruleset's complete details. It projects only
declared fields, requires the exact rule list and parameters, and leaves unrelated
rulesets alone. A missing or denied read is unknown; missing, extra, inactive,
misconfigured, or bypassed managed rules are drift. Either state fails the run. This
mode does not read membership or private inventory and writes only a sanitized receipt
of comparison states and difference paths. The full owner audit remains local and
must stay under ignored `.local/`.

The workflow pins Safe-Settings to commit
`e19444e0d69de050ba55d0262b71fcd8a98edfef`, checks its lockfile SHA-256, and installs
Node 22.23.4 production dependencies without lifecycle scripts before the App key is
referenced. The App ID and private key are scoped to the `governance` Environment, whose
live deployment branch restriction must allow only `main`. Request tracing emits
allowlisted counters, fails if unsupported or if it detects unclassified managed
writes, and excludes the expected Safe-Settings check-run publication. Full
Safe-Settings output is kept only in the ephemeral runner's ignored `.local/` log;
only the sanitized trace receipt and sanitized post-apply comparison are uploaded.

A daily 06:17 UTC schedule is present but its activation flag is
`safe_settings.schedule_enabled: false`. The flag is checked before any workflow step
references the App credentials. Enabling it is a reviewed manifest change after
four-repository readback, an idempotent zero-write rerun, and the canary acceptance
sequence. Scheduled execution has authority only over shared repository settings.
Organization policies and team state remain on the explicit owner CLI path.

The evidence sequence is preview, reviewed apply, independent readback, then a second
apply that produces zero managed configuration writes and still passes independent
readback. Evidence is tied to the manifest and workflow commit. A failed or interrupted
run must be read back before retry; never assume that a timeout means no writes
occurred. Evidence files may be published only after removing membership, private
inventory, credentials and raw API payloads.

## GitHub Free and workspace boundary

The baseline uses public repositories, GitHub-hosted Actions and per-repository
rulesets. It does not claim organization-wide rulesets on GitHub Free. GitHub Free
does not provide organization-owned Codespaces budgets or policies; a committed
`.devcontainer/devcontainer.json` with a digest-pinned image gives repositories a
repeatable default, while a Codespace is owned and billed by its creator. GitHub
controls pushed branches and pull requests, not local worktree directories. These are
declared operating boundaries, not hidden enforcement claims.
