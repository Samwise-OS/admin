# gstack operating patterns for Samwise-OS

**Inspection pin:** [`garrytan/gstack` `de53aef03fbd0811d51cb111c86f8c7ecaf7e57e`](https://github.com/garrytan/gstack/commit/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e), current `main` at inspection (2026-10-30; GitHub API and `git ls-remote` agreed). The official repository is [`garrytan/gstack`](https://github.com/garrytan/gstack), confirmed by its API `full_name`, default branch `main`, and README clone URL. This is source inspection; gstack was not installed or run.

## Findings relevant to a deterministic GitHub factory

The most transferable idea is to make CI evidence part of the control contract. gstack’s free-test workflow says it is a required check, runs on pull requests and pushes to `main`, and has an always-running aggregate named `free-tests`. A planner inventories and balances the suite; shards emit strict result receipts; the aggregate verifies exact planned coverage and every outcome. Uploading the plan/results as artifacts gives the aggregate explicit inputs instead of inferring success from job presence. See [`free-tests.yml`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/.github/workflows/free-tests.yml) and its workflow-wiring contract [`test/free-tests-workflow-wiring.test.ts`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/test/free-tests-workflow-wiring.test.ts). For Samwise-OS, this suggests treating each provision/reconcile/enforcement proof as a receipt with expected scope, observed GitHub state, result, and commit/run identity; a missing receipt should fail acceptance.

The suite explicitly separates secretless checks from paid evaluations. The free lane declares no provider keys and uses read-only `contents` permission because it executes PR-controlled code; a workflow-wiring test fails if secrets appear. The workflow comments also distinguish fork-safe tests from eval lanes that cannot receive repository secrets. Its dispatch and concurrency are keyed by PR number/run ID to avoid same-named branches from separate forks cancelling each other. These are enforceable workflow choices, not just repository guidance. They fit a solo-owner org well: keep policy/schema validation and GitHub-state checks in a secret-minimal required gate, then put paid model work behind a separate, opt-in or narrowly triggered lane.

The paid eval workflow supports PR diff selection and explicit dispatch inputs such as `evals_all`, base SHA, expected SHA, and nonce. The weekly periodic workflow runs the full paid periodic tier, plans duration-balanced slices, and fails closed if a slice artifact is missing; a hollow-shard guard rejects a nominally successful run that executed zero tests. The wiring tests assert planner/executor/report agreement and that slice count and timeout derive from the plan rather than handwritten duplicate constants. See [`evals.yml`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/.github/workflows/evals.yml), [`evals-periodic.yml`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/.github/workflows/evals-periodic.yml), and [`evals-workflow-wiring.test.ts`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/test/evals-workflow-wiring.test.ts). These mechanisms can bound when expensive LLM evaluations run and make completion auditable. The workflow alone does not establish actual provider cost, model behavior, or that every test classification is correct.

## Budgeting and failure telemetry

gstack’s `/ship` budget helper is unusually explicit about its guarantee: it is an **admission cap**, not a hard spend ceiling. Before starting work it compares measured usage, open reservations, unknown charges, projection, tail reserve, and stop overhead with the cap. Parallel dispatch batches are reserved together. Work already admitted can exceed its projection, and the host cannot be stopped mid-turn. Without a configured cap it meters and reports; it does not impose a default. Meters include host counters/journals where available and a calibrated estimate; when a cap is set but no meter is readable, start refuses. See [`docs/ship-budget.md`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/docs/ship-budget.md), [`lib/ship-budget.ts`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e/lib/ship-budget.ts), and the [`ship-budget` tests](https://github.com/garrytan/gstack/tree/de53aef03fbd0811d51cb111c86f8c7ecaf7e/test). This is a useful model for per-run LLM admission, reservations for concurrent calls, explicit unknown-cost accounting, and refusing silent unmetered execution. It does not prove “cheap” execution; that needs actual provider usage and price records, and the documented design itself permits projection overruns.

For flaky tests, the free lane permits a bounded serial retry, records recovered failures in a JSONL ledger, uploads that ledger even when the shard is green, and retains original logs when retry recovered the failure. A retry is visible as a flaky pass rather than erasing the first failure. The weekly health workflow reads seven days of GitHub Actions history and fails when a free test flakes in more than 5% of at least 20 main runs, or the duration seed has more than five untracked test files. It reports unavailable metrics, keeps the tracking issue open if evidence is missing, and closes only when all enforced checks have evidence and pass. See [`free-tests.yml`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e57e/.github/workflows/free-tests.yml) and [`test-health.yml`](https://github.com/garrytan/gstack/blob/de53aef03fbd0811d51cb111c86f8c7ecaf7e/.github/workflows/test-health.yml). Transferable principle: retries may improve availability, but preserve first-failure evidence and feed repeated failures into an enforced trend check.

## What is proven, and what remains a claim

The pinned source proves these mechanisms are implemented in the repository and locally wired to tests. It does **not** prove the currently configured GitHub branch protection actually requires the check, Actions are enabled, scheduled jobs run successfully, or organization-level settings are enforced in a live account. Those require authenticated GitHub inspection and observed runs. In particular, the README’s productivity and shipping-rate figures are author-reported claims; they are not established by the CI source examined here. The source documents a token-budget admission mechanism and its limitations, but no evidence in the reviewed material supports a general claim that model executions are cheap.

For Samwise-OS, borrow the receipt-driven aggregate, secretless required lane, planned execution manifests, fail-closed missing-evidence behavior, admission budget with honest overrun semantics, and retained retry telemetry. Keep the boundary explicit: gstack is an application/tooling workflow; it is not itself a deterministic organization-baseline reconciler or proof of GitHub policy enforcement.
