# GitHub Free organization workspace controls

**Scope/date:** Official GitHub and Git documentation reviewed 2026-10-30. This note covers Codespaces and local Git worktrees; it does not inspect or change the Samwise-OS organization settings.

## Codespaces: plan boundary

GitHub Free organizations have **no included Codespaces quota and cannot pay for organization-owned Codespaces**. Codespaces from public organization repositories are available, and users with repository access can create Codespaces for private organization repositories, but those Codespaces are user-owned and billed to the creator. Consequently, organization spending limits and Codespaces policies cannot govern those user-paid environments. GitHub documents organization Codespaces policy features as available to Team and Enterprise organizations that pay for Codespaces. These policies include access, machine type, maximum per-user organization-billed Codespaces, retention, permitted base images, and forwarded-port visibility. Sources: [plan usage table](https://docs.github.com/en/billing/reference/product-usage-included), [organization Codespaces management](https://docs.github.com/en/codespaces/managing-codespaces-for-your-organization), [ownership and payment](https://docs.github.com/en/codespaces/managing-codespaces-for-your-organization/choosing-who-owns-and-pays-for-codespaces), [enablement by plan](https://docs.github.com/en/codespaces/managing-codespaces-for-your-organization/enabling-or-disabling-github-codespaces-for-your-organization).

This is the consequential limit for the current GitHub Free org slice: do not represent organization-level Codespaces policy, cost caps, retention, or access restrictions as available controls. A user’s personal quota/budget governs user-owned Codespaces; Free/Pro personal included quotas are separate from the organization plan ([Codespaces billing](https://docs.github.com/en/billing/concepts/product-billing/github-codespaces)).

## What can be standardized in repositories

GitHub reads dev-container configuration from each repository. A checked-in `.devcontainer/devcontainer.json` (or root `.devcontainer.json`) is the repository’s default; when creating a repository from a template, GitHub uses that default configuration without offering the user a choice among alternatives. This makes an organization-owned template repository a practical way to seed future repos with the same configuration. It is a convention/template mechanism: it does not set or enforce a central org default for all independently created repositories. See [dev container configuration](https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/adding-a-dev-container-configuration/introduction-to-dev-containers) and [Codespaces template repositories](https://docs.github.com/en/codespaces/setting-up-your-project-for-codespaces/setting-up-your-repository/setting-up-a-template-repository-for-github-codespaces).

For repeatability, commit the devcontainer configuration and pin its base image by immutable digest; version-pin Features and Actions referenced by the configuration where supported. Docker documents that tags can move and digests identify a fixed image ([pull by digest](https://docs.docker.com/reference/cli/docker/image/pull/)); the devcontainer Feature catalog illustrates versioned references ([Features](https://containers.dev/features)). This improves what a repo declares, but GitHub Free organization policy cannot centrally reject a nonconforming config. CI can lint the declaration in repositories whose workflows are enabled, but that is repository workflow enforcement and must itself be required through the live GitHub protection mechanism to gate merges.

## Git worktrees are outside GitHub’s control plane

`git worktree` creates linked working directories and administrative metadata on the machine hosting a local Git repository. The Git documentation describes worktree add/list/remove and metadata under the local repository’s `$GIT_DIR/worktrees`; these are Git operations, not GitHub repository or organization resources ([git-worktree](https://git-scm.com/docs/git-worktree.html)). GitHub can govern pushed branches, commits, and pull requests through its remote repository controls; it cannot enumerate or enforce the paths, lifetime, or local configuration of a developer’s unpushed worktrees. A repository can document recommended worktree commands, but that remains guidance executed on the host.

**Practical boundary:** use a template repository and checked-in devcontainer for a consistent starting point; use repository workflows and verified GitHub rules for remote changes; classify Codespaces owner-level policies and local worktree lifecycle as outside the enforcement authority of a GitHub Free organization.
